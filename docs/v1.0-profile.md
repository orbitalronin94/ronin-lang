# Perfil candidato RONIN Runtime v1.0

**Estado:** propuesta de alcance para revisión; no es todavía una declaración de conformidad ni modifica MDES.  
**Base:** rama `work/v1.0-diagnostic-foundation`.  
**Principio:** v1.0 estabiliza un perfil implementable y verificable; no pretende convertir automáticamente todas las extensiones futuras de MDES en características disponibles.

## 1. Objetivo y regla de inclusión

Una capacidad entra en el perfil estable solo si tiene:

1. contrato semántico inequívoco;
2. implementación en los runtimes que declaran soportarla;
3. tests positivos y negativos;
4. paridad cruzada cuando exista implementación Python y Rust;
5. documentación de entradas, salidas, errores y limitaciones.

Una sección de MDES, una API con nombre parecido o un prototipo no bastan para declarar soporte.

## 2. Perfil del lenguaje

### 2.1 Incluido en el candidato

- Declaraciones `system` con `parts`, `resource`, `agents` y `params`.
- Agentes con `phi`, `psi`, `frequency` y metadata.
- Valores escalares numéricos, booleanos, cadenas y null en contextos admitidos.
- Arrays y objetos anidados en metadata y valores donde el parser los admite.
- Parámetros del runtime documentados por el parser y validador.
- Rechazo de campos desconocidos y duplicados en bloques tipados.

Este es un lenguaje de descripción de sistemas, no todavía un lenguaje de propósito general.

### 2.2 Fuera del perfil candidato

No se anunciarán como implementados: funciones puras/impuras generales, expresiones, condicionales, bucles, módulos/imports, macros, DSL de auditoría, instrucciones plot, actores, canales, futures/promises, await, streams con backpressure ni un sistema general de tipos de usuario.

## 3. Perfil numérico

### 3.1 Modelos disponibles

El subconjunto compartido Python/Rust incluye:

- `pusfre`;
- `ces`;
- `hill`;
- `ces_hill`;
- `full` únicamente en el orden temporal actualmente soportado.

La implementación CES usa pesos iguales para los tres componentes. No existe todavía una sintaxis normativa para pesos CES configurables; no se anunciarán pesos arbitrarios como capacidad disponible.

### 3.2 Restricciones explícitas

- Los rangos y la coherencia de parámetros se validan antes de resolver.
- La saturación Hill con `K = inf` se reduce a identidad.
- El límite CES próximo a cero usa media geométrica ponderada en el código actual. Esto no es automáticamente equivalente a la fórmula PUSFRE.
- `full` con memoria temporal de orden superior a 1 se rechaza explícitamente; no se aproxima silenciosamente.
- El estimador de deuda no está implementado: `debt` se informa como `null`.
- La semántica completa de coexistencia y el contrato de deuda deben revisarse contra la fuente normativa íntegra antes de declarar conformidad total.

### 3.3 Resoluciones normativas pendientes

| ID | Cuestión | Condición para incluir en v1.0 |
|---|---|---|
| MATH-001 | CES `lambda → 0` frente a PUSFRE | Decisión normativa única, con vectores numéricos y tests en ambos runtimes |
| MATH-002 | Dominio de `lambda`, valor cero y casos especiales | Dominio y excepciones coherentes entre parámetros, norma y ejemplos |
| MATH-003 | Pesos CES | Confirmar pesos iguales como contrato estable o especificar cómo se declaran y validan |
| MATH-004 | Deuda y coexistencia | Definir fórmula, entradas, unidades y comportamiento de borde; de lo contrario, deuda queda fuera |
| MATH-005 | Memoria temporal | Definir kernel, inicialización, actualización y estabilidad antes de soportar orden superior |

No se resolverá ninguna de estas cuestiones mediante una fórmula inventada en el runtime.

## 4. Simulación

El candidato incluye el kernel de simulación disponible con semilla reproducible, salida de historial, estado final, eventos de extinción y survivability. La compatibilidad se expresa mediante invariantes y tolerancias compartidas; no se promete identidad de secuencias aleatorias entre runtimes salvo que el contrato y las pruebas la demuestren.

La memoria temporal de orden superior queda excluida hasta completar MATH-005.

## 5. Diagnóstico e identificabilidad

### 5.1 Diagnóstico de sistema

El comando `diagnose` informa rango de Ω, estado de degeneración, indicadores de identificabilidad y recomendación. La regla de tres órdenes es la heurística prescrita por el anexo normativo actual; no debe describirse como prueba universal de identificabilidad estructural.

Con menos de dos valores Ω positivos, el estado es `unknown`. Los runtimes comparten fixtures y paridad para estados activo, inactivo y desconocido.

Los indicadores `K` y `alpha_h` se derivan hoy de los valores/configuración del modelo. La especificación del lenguaje todavía no expresa inequívocamente la diferencia entre un parámetro libre y otro fijado explícitamente por el usuario. Esa distinción debe resolverse antes de atribuir a esos booleanos significado inferencial fuerte.

### 5.2 Diagnóstico local pre-ajuste

Las APIs de identificabilidad en Python y Rust incluyen:

- diseño Hill local desde Ω, K, alpha_h y escala de ruido;
- motor genérico desde Jacobiano, pesos y escalas paramétricas;
- perfil SIR con subreporte en la aproximación de fase temprana.

Los informes separan rango local de identificabilidad estructural global. El perfil SIR informa las combinaciones identificables bajo su aproximación; no estima individualmente parámetros que el modelo reducido no identifica.

Estas APIs no equivalen todavía a un lenguaje de diagnóstico general ni a ajuste de parámetros.

### 5.3 Bootstrap

El bootstrap no está implementado. Solicitudes `bootstrap > 0` se rechazan explícitamente; `bootstrap_ci` permanece `null`. No se aceptará un parámetro de CLI que aparente ejecutar un procedimiento inexistente.

## 6. CLI e IR

El perfil candidato contempla los comandos presentes en las implementaciones compartidas: `list`, `check`, `solve`, `run`, `compile`, `diagnose` y `simulate`. El REPL Python se documenta como herramienta adicional, no como intérprete general de RONIN.

El JSON IR actual declara `format = "ronin-ir"` e `ir_version = 1`. Antes de estabilizarlo se requiere:

- esquema formal y publicado;
- política de campos obligatorios/opcionales;
- tratamiento normativo de infinitos y valores no finitos;
- pruebas de round-trip donde sea semánticamente posible;
- compatibilidad hacia delante/atrás y política de cambios incompatibles.

La paridad de fixtures actual no sustituye por sí sola a un esquema versionado completo.

## 7. Capacidades excluidas de v1.0 salvo decisión expresa

- catálogo completo de más de 160 tipos de dominio y tipos dependientes;
- ejecución general de funciones, control de flujo y macros;
- concurrencia de actores, canales, futures, promises y backpressure;
- interoperabilidad DSL con Python/Rust, SQL, REST, GraphQL, WebSockets, gRPC y formatos de datos generales;
- backends WASM, C, LLVM, JVM, .NET IL y JavaScript;
- RONIN Office;
- estimador de deuda, bootstrap, ajuste general y perfiles de verosimilitud;
- memoria temporal de orden superior.

Estas capacidades permanecen en la visión y el roadmap; excluirlas del primer perfil estable no equivale a descartarlas del proyecto.

## 8. Criterios de aceptación para declarar v1.0

- [ ] Aprobar este perfil o una versión revisada del mismo.
- [ ] Cerrar MATH-001 a MATH-005 o excluir explícitamente del perfil los contratos no resueltos.
- [ ] Completar la matriz de conformidad requisito por requisito para el perfil aprobado.
- [ ] Cerrar diferencias de parser, validación, solver, diagnóstico, simulación, CLI e IR entre Python y Rust.
- [ ] Añadir property-based tests y fuzzing para lexer/parser y validadores.
- [ ] Definir errores estructurados y códigos de salida estables para ambos CLIs.
- [ ] Formalizar el esquema IR v1 y sus pruebas de compatibilidad.
- [ ] Verificar instalación, empaquetado y ejecución desde entornos limpios.
- [ ] Publicar documentación de usuario, referencia del lenguaje, API, arquitectura, límites y migración.
- [ ] Ejecutar CI completa y publicar artefactos reproducibles.
- [ ] Crear release candidate, congelar el alcance y resolver todos los bloqueos de lanzamiento.

## 9. Relación con el corpus Papers

Los trabajos de Papers alimentan el método de diagnóstico, la distinción entre rango local y afirmaciones estructurales, la necesidad de pre-registrar pruebas refutables y la delimitación explícita de los dominios de validez. Sus resultados no se convierten automáticamente en axiomas del lenguaje: cada derivación que afecte a semántica normativa necesita revisión, hipótesis explícitas y pruebas reproducibles.

La integración específica y sus límites se registran en [research-integration-identifiability.md](research-integration-identifiability.md).
